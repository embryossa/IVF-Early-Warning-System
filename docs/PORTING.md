# PORTING.md — перенос с чернового стенда на лабораторную машину

Проект разрабатывается на домашнем ПК (`environment: draft`) и переносится на машину в
лаборатории (`environment: production`). Конструкция рассчитана так, что перенос — это
правка **одного файла** плюс проверки ниже.

## 0. Проект автономен

На лабораторной машине нет проекта `embryo-lab-data` и не установлен TabPFN. Ни то,
ни другое ставить не нужно: всё вендорено внутрь.

| что вендорено | где | зачем |
|---|---|---|
| `kpi`, `privacy`, `incubator`, `lots`, `_io`, клиент Teable | `src/ews/vendor/` | пороги Венского консенсуса, HMAC, разбор логов MIRI, лоты, REST |
| TabPFN-3: скрипт, веса, окружение | `external/tabpfn/` | конверт P10–P90 |

Из Digital Twin нужны **только итоговые вероятности** (`PRAI`, `DIGITAL TWIN`), и они
приходят в мастер-таблице OPU. Сам пайплайн DT запускать не требуется — медленный
контур подтверждения по исходу читает их из выгрузки.

Проверить вендор:

```bash
python scripts/ews_sync_vendor.py --check      # без источника — штатно для лаборатории
python scripts/ews_setup_tabpfn.py --clinic <code> --check
```

`ews_sync_vendor.py --check` сверяет контрольные суммы. Вендоренные файлы — **копии,
а не форк**: править их на месте запрещено, изменения делаются в `embryo-lab-data` и
переносятся `--sync --from <путь>` на машине, где источник есть. Иначе одна и та же
клиника посчитает свои KPI по-разному в двух проектах, и заметить это будет нечем.

## 0a. Единица переноса — папка, а не `git clone`

Два куска в git не входят и через `git clone` не приедут:

| что | размер | почему не в git |
|---|---|---|
| `external/tabpfn/models/*.ckpt` | 233 МБ | слишком тяжело для репозитория |
| `data/<clinic>/local_private/dev_cohort.xlsx` | ~1 МБ | обучающая когорта — данные пациенток |

**Поэтому переносится каталог целиком** (архив, внешний диск, сетевая папка), а не
репозиторий. Что можно не копировать: `external/tabpfn/.venv/` (венвы не переносимы
между машинами — пути внутри абсолютные, создаётся заново по `requirements.txt`),
`data/*/` кроме `local_private/dev_cohort.xlsx`, `__pycache__`.

Проверить готовность до и после переноса:

```bash
python scripts/ews_setup_tabpfn.py --clinic <code> --check
```

Он перечисляет ровно то, чего не хватает, и что именно копировать. Собрать вендор на
исходной машине (если он ещё не собран):

```bash
python scripts/ews_setup_tabpfn.py --clinic <code> --vendor-from <каталог рабочего TabPFN>
```

Веса читаются из `external/tabpfn/models` через `TABPFN_MODEL_CACHE_DIR` —
скачивания из сети не будет. Это сознательно: лабораторная машина может не иметь
выхода в интернет, а молчаливая попытка скачать 233 МБ посреди суточного прогона
выглядит как зависание, а не как понятная ошибка.

Данные пациенток машину не покидают: скрипт использует только локальный пакет
`tabpfn`, обращений к облачному `tabpfn_client` в нём нет (проверено, 0 вхождений).

## 1. Что переносится и что нет

| Файл | В git | Правится при переезде |
|---|---|---|
| `config/settings.yaml` | да | **нет** — если пришлось, параметр лежит не в том файле |
| `config/machine.local.yaml` | нет | **да, целиком** — это и есть перенос |
| `config/settings.local.yaml` | нет | да — токены лабораторной машины |
| `config/consensus/*.yaml` | да | нет |
| `src/`, `scripts/`, `docs/`, `.claude/` | да | нет |
| `data/` | нет | не переносится: боевые данные живут только в лаборатории |
| Калиброванные `h` в `settings.yaml` | да | **см. §4 — переносить нельзя** |

## 2. Чек-лист переноса

1. `git clone` / копирование репозитория без `data/`.
2. `cp config/machine.local.yaml.example config/machine.local.yaml` и заполнить:
   - `environment: production`;
   - `embryo_lab_data.project_dir` → **оставить пустым**: проект автономен, модули
     вендорены. Поле нужно только на машине разработки, для
     `ews_sync_vendor.py --check`;
   - `digital_twin.project_dir`, `tabpfn_regression.project_dir` + рабочие `run_cmd`;
   - `teable.url` / `base_id` / `opu_table_id` лабораторного Teable;
   - `airtable.*` для базы расходников и лотов;
   - `miri_logs.dump_dir` — каталог недельной выгрузки (на черновом стенде был пуст);
   - `consensus.pdf_dir` — каталог PDF консенсусов.
3. `cp config/settings.local.yaml.example config/settings.local.yaml`, вписать токены,
   выставить `enabled.teable: true`, `enabled.airtable: true`.
4. В `config/settings.yaml` включить `soft_steps.miri.enabled: true` — это единственная
   правка `settings.yaml`, допустимая при переезде, и она отражает реальное различие
   стендов, а не путь.
5. `python scripts/preflight.py` — обязателен, см. §3.
6. `python scripts/ews_backfit.py` — обязателен, см. §4.
7. `python scripts/ews_run.py --dry-run` — читает свежую строку цикла и печатает её
   псевдонимизированной. Если в выводе видно ФИО или паспортный ID — стоп, разбор
   границы ingest, дальше не идти.

## 3. Preflight

Не формальность. В соседнем проекте расхождение окружения с `requirements.txt` трижды
давало **молчаливо пропущенный шаг** вместо ошибки, и один раз это стоило неверного вывода
в отчёте, а не только времени. `preflight.py` проверяет:

- фактически установленные пакеты против `requirements.txt`;
- отдельно — импорт пакетов, чьё отсутствие даёт мягкий отказ (шаг тихо пропускается);
- существование каждого пути из `machine.local.yaml` с учётом гейтов `enabled`;
- доступность Teable по REST и наличие таблицы OPU;
- совпадение версии контрактов `embryo-lab-data` с ожидаемой.

Прогон не начинать, пока preflight не вернул 0.

## 4. Калибровка не переносится

`h_watch` / `h_alert`, найденные на черновом стенде, **непригодны в лаборатории**: они
подобраны под объём и разброс той выгрузки, что была под рукой дома. Перенос чужих порогов
— это ровно тот способ получить либо молчащую, либо кричащую систему.

Поэтому при переезде:

1. `thresholds.calibrated` сбрасывается в `false` (и остаётся таким, пока не отработает
   бэкфит на лабораторных данных);
2. пока `calibrated: false`, система выдаёт только `watch` — `alert` физически недоступен;
3. `scripts/ews_backfit.py` пересчитывает `h` на лабораторной истории и записывает
   `calibrated_at`, `calibration_window`, `measured_false_alarm_rate`.

То же правило действует при существенном изменении объёма лаборатории, смене основной
модели конверта или её переобучении: калибровка привязана к конкретному распределению
остатков, а не к проекту.

## 5. Чем черновой стенд отличается по поведению

| | draft (дом) | production (лаборатория) |
|---|---|---|
| Уровень тревоги | только `watch` | `watch` и `alert` |
| Штамп артефактов | `environment=draft` на каждом файле | `environment=production` |
| Среда (MIRI) | выгрузки нет, шаг выключен | недельная выгрузка, шаг включён |
| Данные | учебные/устаревшие выгрузки | боевая мастер-таблица |
| Назначение отчётов | проверка кода | принятие решений в лаборатории |

Штамп обязателен именно потому, что HTML-панель чернового стенда визуально неотличима от
лабораторной. Черновой отчёт, принятый за боевой, — тот же класс ошибки, ради
предотвращения которого строится вся система.
