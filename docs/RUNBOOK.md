# RUNBOOK.md — запуск EWS на новой лаборатории

Вся логика проверок и подбора порогов параметризована профилем клиники. Запуск на
другой лаборатории **не требует правок кода** — только нового профиля и повторения
последовательности ниже. Ни один шаг не начинается с нуля: то, что уже измерено на
других клиниках (калибровка конверта), переиспользуется, а то, что специфично для
лаборатории (базовые доли, пороги), пересчитывается обязательно.

## Что переиспользуется, а что считается заново

Проект автономен: `embryo-lab-data` и TabPFN на лабораторной машине не нужны, всё
вендорено внутрь (`src/ews/vendor/`, `external/tabpfn/`). Из Digital Twin берутся
только итоговые вероятности, и они приходят в мастер-таблице OPU.

| Величина | Источник | Почему так |
|---|---|---|
| Математика карт, целевые частоты ложных тревог, правила чекпойнтов | `config/settings.yaml` — общий | это МЕТОД, он не зависит от лаборатории |
| Пороги Венского консенсуса | `embryo.kpi.KPI_SPECS` | универсальны по определению |
| Масштаб остатка конверта, покрытие P10–P90 | все доступные клиники сразу | свойство МОДЕЛИ, не лаборатории; однородность проверяется, а не предполагается |
| Базовые доли (p₀ по контурам) | **только своя клиника** | BlR соседней лаборатории не является вашим BlR ни в каком приближении |
| Пороги карт `h_watch` / `h_alert` | **только своя клиника** | зависят от её объёма и разброса; чужие непригодны |
| Набор карт | профиль клиники | зависит от объёма: каждая лишняя карта ужесточает пороги всем |

## Шаг 1. Профиль клиники

```bash
cp -r config/clinics/_template config/clinics/<code>
```

Заполнить два файла:

- **`clinic.yaml`** — код, имя, часовой пояс, опорное окно, набор карт, гейты источников.
- **`columns.yaml`** — соответствие «колонка выгрузки → каноническое имя».
  Имена берутся РОВНО как в выгрузке, включая висячие пробелы и регистр.
  Канонические имена слева не переименовывать: они совпадают с `embryo-lab-data`,
  и именно поэтому модули `kpi` / `ozema` / `regression_qc` принимают кадр без
  переходников.

Отсутствующая колонка не угадывается: она попадёт в предупреждение, а метрики,
которым она нужна, окажутся недоступны явно. Это лучше, чем посчитать KPI по
подвернувшемуся столбцу.

**Опорное окно.** Период, который владелец лаборатории объявляет эталонным. Слишком
короткое даст широкую неопределённость центра, и бэкфит поднимет пороги (честно, но
детекция замедлится). Слишком длинное рискует вобрать в норму реальный сдвиг — шаг 3
такие случаи находит и печатает, но решение остаётся за владельцем.

## Шаг 2. Инфраструктура

```bash
cp config/machine.local.yaml.example config/machine.local.yaml   # пути ЭТОЙ машины
cp config/settings.local.yaml.example config/settings.local.yaml # токены
python scripts/ews_sync_vendor.py --check                        # вендор модулей
python scripts/ews_setup_tabpfn.py --clinic <code> --check       # вендор модели
python scripts/preflight.py
python scripts/ews_bootstrap_opu.py --clinic <code>              # база в Teable
python scripts/ews_sync_opu.py --clinic <code>                   # наполнить
```

`preflight.py` обязателен и не формальность: он отдельно проверяет пакеты, отсутствие
которых даёт МЯГКИЙ отказ — тихо пропущенный шаг вместо ошибки.

`ews_setup_tabpfn.py --check` перечисляет, чего не хватает модели конверта на этой
машине. Если чего-то нет — конверт просто не регистрируется, а прогон EWS идёт без
него (мягкий шаг). Модель вендорена в `external/tabpfn/`, отдельно её ставить не
нужно; веса и обучающая когорта переносятся вместе с ПАПКОЙ проекта, а не через git
(см. `docs/PORTING.md` §0). Окружение модели создаётся на новой машине заново:

```bash
python -m venv external/tabpfn/.venv   # Python 3.10+, подходит системный
external/tabpfn/.venv/Scripts/python.exe -m pip install --index-url https://download.pytorch.org/whl/cpu torch==2.7.0
external/tabpfn/.venv/Scripts/python.exe -m pip install -r external/tabpfn/requirements.txt
```

## Шаг 3. Опорные измерения

```bash
python scripts/ews_baseline.py --clinic <code>
```

Даёт три вещи:

1. **Базовые KPI лаборатории** по всей истории — против Венских порогов.
2. **In-control параметры опорного окна** (`incontrol_parameters.json`) — центр
   относительного контура, плюс сравнение с периодом до окна.
3. **Калибровку конверта** — покрытие P10–P90 и разброс остатков по всем клиникам.

**Читать в первую очередь — `baseline_caveats`.** Если окно вобрало значимый сдвиг,
скрипт скажет об этом прямо: карта на такой метрике центрирована на новом уровне и
прошлый сдвиг не увидит. Дальше два законных пути:

- сдвиг объясним и объяснение известно → внести его в `reference_window.declared_shifts`
  профиля. Объяснение НЕ отменяет оговорку, оба текста живут в манифесте рядом;
- сдвиг подозрителен → сдвинуть границу окна и пересчитать.

Отдельно проверить: не попала ли на карту метрика с **субъективным знаменателем**.
Классический случай — OCCR: его знаменатель, число фолликулов, — субъективный счёт
врача, он дрейфует вместе с практикой счёта и имитирует сдвиг процесса. В шаблоне он
уже исключён. Профиль не даст поставить такую метрику на карту: проверка падает с
ошибкой при загрузке.

## Шаг 4. Подбор порогов

```bash
python scripts/ews_backfit.py --clinic <code> --replicates 4000 --write
```

Решает обратную задачу: цели заданы сверху (`settings.thresholds.
target_false_alarms_per_year`), `h` вычисляется под них симуляцией. Ничего не берётся
из литературы.

Что проверить в выводе:

- **достигнутые частоты** близки к целевым по системе целиком (цели совместные:
  каждая карта получает `цель / m`);
- **задержка детекции** приемлема. Если медиана до `alert` превышает 1–1.5 месяца при
  сдвиге шансов вдвое — объём лаборатории мал для такого числа карт. Правильный рычаг —
  **сократить число карт**, а не ослабить цель: меньше карт дают одновременно и меньше
  ложных тревог, и более низкий порог;
- **оговорки базовой линии** перенеслись в манифест калибровки.

Пороги пишутся в `config/thresholds.<code>.local.yaml` — сгенерированный файл в
`.gitignore`. Руками не править: затрётся следующим бэкфитом. В git он не попадает
намеренно, чтобы чужие пороги физически не могли уехать в другую лабораторию.

## Шаг 5. Прогон

```bash
python scripts/ews_run.py --clinic <code> --replay   # ретроспектива по всей истории
python scripts/ews_run.py --clinic <code>            # суточный, инкрементальный
```

`--replay` пересобирает состояние карт с нуля хронологически — это способ увидеть,
что система сказала бы на уже прожитой истории, до боевого запуска. Порядок циклов
обязателен: карта секвенциальна.

**Ожидаемая картина при первом replay.** Если опорное окно — не вся история, карты
будут сигналить на периоде ДО окна. Это не ложные тревоги: карта честно говорит, что
тогда лаборатория отличалась от того, что сейчас считается нормой. Сравнивать
измеренную частоту ложных тревог с целевой нужно **только внутри опорного окна**.

## Шаг 5а. Contexts и медленный контур

`ews_run.py` собирает confounders (среда MIRI, лоты расходников) **только для
сработавших циклов** — их единицы, тогда как разбор логов всей когорты занимает
минуты. Границы «необычного» берутся из `data/<clinic>/state/confounder_baseline.json`,
который пересчитывает недельный проход `ews_enrich_miri.py`. Пока базы нет,
подтверждение по среде недоступно, и тревога об этом прямо говорит.

**Абсолютных порогов по среде не бывает.** Измерено на 49 циклах: критический эпизод
есть у 100% циклов (за шесть суток на шести камерах открытие крышки — рутина).
Различает нагрузку только её объём: критические минуты, медиана 103 против верхнего
дециля 1916. Границы пересчитываются по когорте на каждом недельном проходе.

Медленный контур (`outcome.py`) сравнивает предсказанную вероятность беременности
(`PRAI`, `DIGITAL TWIN` из выгрузки) с фактическим исходом. Тревог он не поднимает:
исход зависит от переноса, эндометрия и десятка вещей вне лаборатории. Его роль —
подтверждать или опровергать тренды быстрого контура, и при нехватке исходов он
честно отказывается от вывода.

Рядом с ним — тот же контур **с поправкой на пациенток** (`outcome_ra.py`,
`docs/METHODOLOGY.md` §3.5): факт против ожидания DT, VLAD, RA-CUSUM и O/E по
месяцам, эмбриологам, нагрузке средой и лотам Airtable. Новых шагов в расписании нет —
он считается внутри `ews_run.py`. Что нужно для полного набора разрезов:

- колонки `Preg` и `DIGITAL TWIN` в мастер-таблице (уже синхронизируются в Teable);
- `enabled.airtable: true` и токен в `settings.local.yaml` — лоты;
- недельный проход `ews_enrich_miri.py` — разрез по среде читает его
  `ews_window_context.csv` и границы `confounder_baseline.json`.

Сдвиг DT на клинику замораживается сам, как только наберётся 40 исходов
(`data/<clinic>/state/outcome_calibration.json`). До этого ожидание — DT без поправки.

## Шаг 6. Когда пороги надо пересчитать

`calibrated` сбрасывается, и система возвращается в режим только `watch`, при любом из:

- перенос на другую машину или в другую лабораторию (гейт проверяет
  `calibrated_environment` автоматически — см. `docs/PORTING.md` §4);
- переобучение или замена модели конверта;
- существенное изменение объёма лаборатории;
- добавление карты на панель.

## Про риск-коррекцию: гейт закрыт, и это проверено

Конверт регистрируется и замораживается, но карты идут на базовой доле лаборатории,
а не на индивидуальном прогнозе. Причина измерена на этих данных: прогноз хорошо
предсказывает СЧЁТ (корреляция 0.86-0.97) и не предсказывает ДОЛЮ (0.13 / -0.08 /
0.16) — а риск-коррекции нужна именно доля. Высокая корреляция счёта объясняется
знаменателем: и факт, и прогноз растут вместе с числом ооцитов.

На новой лаборатории эту проверку стоит повторить (`ews_baseline.py` печатает
разнородность до и после), но ожидать другого результата от той же модели не следует.
Открывать `envelope.risk_adjustment_enabled` можно только если corr(доля) окажется
заметно положительной. Подробно — `docs/METHODOLOGY.md` §5.8-5.9.

## Что почти наверняка пойдёт не так на новой лаборатории

1. **Колонки называются иначе, чем ожидалось.** Симптом — предупреждение «колонок нет
   в выгрузке» и пустые метрики. Лечится только `columns.yaml`, не кодом.
2. **`numerator > denominator`** на ClR или MIIR. Это НЕ порча данных: `ClR > 100%` —
   про тайминг проверки оплодотворения, `MII > ОКК` — про добавленные размороженные
   ооциты. Карта на такой метрике не строится (доля вне [0,1] не является
   вероятностью), но сама метрика остаётся в абсолютном контуре.
3. **Опорное окно слишком короткое.** Симптом — широкий CI базовой доли и высокие
   пороги. Лечится расширением окна, если владелец готов назвать больший период
   эталонным.
4. **Карт слишком много для объёма.** Симптом — задержка детекции в месяцах. Лечится
   сокращением `charts.cusum` в профиле.
